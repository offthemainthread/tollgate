# Incoming Event Schema

Tenants report usage by sending a batch of events to the ingestion service.

`POST /v1/events`

## Headers

| Header          | Value              |
| --------------- | ------------------ |
| `Authorization` | `Bearer <API_KEY>` |
| `Content-Type`  | `application/json` |

The tenant is identified from the API key. It is never read from the request body.

## Body

A JSON array of 1 to 500 events. The maximum body size is 1 MB. A single API call can contain multiple events.

```json
[
  {
    "idempotency_key": "usage-2026-10-05-14:00-acme",
    "meter": "api_calls",
    "quantity": 1000,
    "timestamp": "2026-10-05T14:00:00Z"
  }
]
```

### Event fields

| Field             | Type    | Required | Rules                                                                                          |
| ----------------- | ------- | -------- | ---------------------------------------------------------------------------------------------- |
| `idempotency_key` | string  | yes      | 1 to 255 characters from `A-Z a-z 0-9 _ . : -`. Unique per tenant. Generated by the tenant.    |
| `meter`           | string  | yes      | 1 to 255 characters, same character set. Must be one of the tenant's meters.                   |
| `quantity`        | integer | yes      | Whole number from 1 to 1,000,000,000. No decimals, zero, or negative values.                   |
| `timestamp`       | string  | yes      | RFC 3339 in UTC with a `Z` suffix. When the usage happened (event time), not when it was sent. |

The limits above are defaults and are configurable.

**Timestamp window:** no more than 5 minutes in the future (clock skew) and no more than 35 days in the past, measured from when the request is received. This is only a sanity check. What happens to a late event for an already-invoiced period is decided downstream by the aggregator.

### Meters

A tenant can have multiple meters. `meter` is the name of one of that tenant's meters. Names are unique per tenant, so two tenants can each have a meter called `api_calls`. An event for a meter the tenant does not have is rejected with `unknown_meter`.

### Idempotency

The tenant generates the `idempotency_key`, and a retry of the same event must reuse the same key. Do not generate a new key on each retry attempt.

- Same key and identical contents (`meter`, `quantity`, `timestamp`): treated as a duplicate. It is not counted twice, and the result is `duplicate`.
- Same key but different contents: rejected with `idempotency_conflict`. This is a client bug.
- The same key appearing twice in one batch follows the same rules. The first occurrence wins.

## Response

If the request itself is valid, the response is `202 Accepted` with one result per event, in the same order as the request.

```json
{
  "results": [
    { "index": 0, "idempotency_key": "a1", "status": "accepted" },
    { "index": 1, "idempotency_key": "a2", "status": "duplicate" },
    {
      "index": 2,
      "idempotency_key": "a3",
      "status": "rejected",
      "error": {
        "code": "unknown_meter",
        "message": "Meter 'api_cals' does not exist for this tenant"
      }
    }
  ]
}
```

| Status      | Meaning                                                                              |
| ----------- | ------------------------------------------------------------------------------------ |
| `accepted`  | The event was accepted and queued for processing.                                    |
| `duplicate` | An identical event was already received. Nothing is counted twice. Treat as success. |
| `rejected`  | The event was invalid and was not accepted. Do not retry it unchanged.               |

`202` means the request was processed, not that every event was accepted. Clients must check each result, because a batch in which every event is rejected still returns `202`.

### Per-event error codes

| Code                      | Cause                                                |
| ------------------------- | ---------------------------------------------------- |
| `invalid_idempotency_key` | Missing, too long, or contains disallowed characters |
| `unknown_meter`           | The tenant has no meter with this name               |
| `invalid_quantity`        | Not an integer, or outside the allowed range         |
| `invalid_timestamp`       | Not RFC 3339 UTC, or outside the allowed window      |
| `idempotency_conflict`    | Same key as an earlier event but different contents  |

### Request-level errors

If the request itself is bad, no events are processed and the response is an error status with this body:

```json
{
  "error": {
    "code": "not_an_array",
    "message": "request body must be a JSON array of events"
  }
}
```

| Code                     | HTTP status | Cause                                                   |
| ------------------------ | ----------- | ------------------------------------------------------- |
| `unsupported_media_type` | `415`       | `Content-Type` is not `application/json`                |
| `invalid_json`           | `400`       | Empty body, malformed JSON, or data after the array     |
| `not_an_array`           | `400`       | Body is valid JSON but not an array                     |
| `empty_batch`            | `400`       | The array is empty (or the body is `null`)              |
| `batch_too_large`        | `413`       | More than 500 events                                    |
| `body_too_large`         | `413`       | Body larger than 1 MB                                   |

### HTTP status codes

| Status | Meaning                                                       | Retry?               |
| ------ | ------------------------------------------------------------- | -------------------- |
| `202`  | Request processed. Check the per-event results.               | n/a                  |
| `400`  | Malformed JSON, body is not an array, or the array is empty   | No                   |
| `401`  | Missing or invalid API key                                    | No                   |
| `413`  | More than 500 events or body larger than 1 MB                 | No (split the batch) |
| `415`  | `Content-Type` is not `application/json`                      | No                   |
| `429`  | Rate limited. Honour the `Retry-After` header.                | Yes                  |
| `503`  | A dependency is unavailable. Honour the `Retry-After` header. | Yes                  |

When retrying after `429` or `503`, resend the whole request with the same idempotency keys. This is safe: events that were already received come back as `duplicate`.

## Implementation notes (ingest-go)

Processing order: authenticate, rate limit, request-level checks, per-event validation, dedupe, publish.

- **Meter validation.** The service keeps a cached tenant profile (tenant ID, meter names, rate limit) loaded from `billing-spring`. It is fetched once per request. If a meter is not found, the cache is refreshed once and checked again before rejecting. Refreshes are limited to one per tenant every 10 to 30 seconds and are shared between concurrent requests (`singleflight`). If `billing-spring` is down, a stale cached profile is used. With no cached profile at all, the request fails with `503`.
- **Dedupe.** Redis `SET NX` on `idem:{tenant}:{key}` with a TTL. The stored value is a hash of (`meter`, `quantity`, `timestamp`) so a conflicting reuse of the key can be detected. If publishing to Kafka fails, delete the key. The Postgres unique constraint on (tenant, idempotency key) is the authoritative check.
- **Kafka failure.** If publishing fails partway through a batch, the whole request fails with `503`. Retrying is safe.
- **First slice.** Before `billing-spring` exists, meter validation goes through a `MeterRegistry` interface with a static implementation.
